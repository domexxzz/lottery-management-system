## ปิดแล้ว — ทีมพัฒนาตัดสินใจเอง

ข้อเหล่านี้เป็นการตัดสินใจทางเทคนิคที่ไม่ต้องรอธุรกิจ บันทึกไว้เพื่อให้ตรวจย้อนหลังได้
และ**แก้ได้ถ้าฝ่ายธุรกิจไม่เห็นด้วย**

### T-1 · Stack — Next.js 16 + TypeScript + Prisma 7 + PostgreSQL

**เหตุผล** ตรงกับสถาปัตยกรรมที่เอกสาร CTO บทที่ 6 เสนอไว้ (Responsive Web, Modular API,
PostgreSQL) และใช้โค้ดเบสเดียวครอบทั้ง frontend กับ API ลดงาน deploy

**ข้อควรระวัง** `prisma@latest` จะดึง CLI ยุค Prisma 8 (RC) ซึ่งเข้ากันไม่ได้กับ client 7
ปักหมุดไว้ที่ `prisma@7.10.1` แล้ว อย่ารัน `npm update` โดยไม่ตรวจ

### T-2 · เก็บอัตราจ่าย ณ เวลายืนยันบิล (payoutRateSnapshot)

**เหตุผล** หลักการ "คำนวณซ้ำได้" ในเอกสารบทที่ 1 — คำนวณย้อนหลังต้องได้ผลเดิม
แม้ rulebook จะเปลี่ยนไปแล้ว

**พิสูจน์แล้ว** เปลี่ยนอัตราจ่ายรางวัลที่ 1 จาก 900 เป็น 850 แล้วบิลที่ยืนยันก่อนหน้า
ยังคงใช้ 900 ตามเดิม

### T-3 · Audit เขียนในทรานแซกชันเดียวกับข้อมูล

**เหตุผล** ถ้าแยกกัน จะเกิดกรณี audit มีแต่ข้อมูลไม่เปลี่ยน หรือกลับกัน
ทำให้ Audit Log เชื่อถือไม่ได้ ซึ่งขัดหลักข้อแรกของเอกสาร

### T-4 · ค่าเงินทุกช่องเป็น Decimal ไม่ใช้ float

**เหตุผล** float ทำให้ 0.1 + 0.2 ได้ 0.30000000000000004 ซึ่งยอมรับไม่ได้ในระบบการเงิน
มี test ยืนยันข้อนี้

### T-5 · เปิดบิลของ Agent รายอื่นตอบ 404 ไม่ใช่ 403

**เหตุผล** 403 เท่ากับยืนยันว่าบิลเลขนั้นมีอยู่จริง ซึ่งเป็นข้อมูลรั่ว

### T-6 · ปิดรอบแล้วยกเลิกบิลร่างที่ค้างอัตโนมัติ

**เหตุผล** ร่างที่ค้างหลังปิดรอบยืนยันไม่ได้อีกแล้ว ปล่อยไว้ทำให้รายงานสับสน

### T-11 · ค่าตั้งต้นของสูตรการเงิน — ใช้ไปก่อนโดยยังไม่มีลายเซ็น

ฝ่ายธุรกิจสั่งให้เดินหน้าโดยใช้ค่าที่ทีมเห็นว่าเหมาะสม ทีมจึงเลือกค่าต่อไปนี้
และรวมไว้ที่ `src/lib/money.ts` **จุดเดียว** เพื่อให้แก้ได้โดยไม่ต้องไล่ทั้งระบบ

| หัวข้อ | ค่าที่เลือก | เหตุผล |
|---|---|---|
| ทศนิยม | 2 ตำแหน่ง | หน่วยเงินคือบาทและสตางค์ |
| วิธีปัด | ปัดครึ่งขึ้น | คนทั่วไปเข้าใจตรงกันที่สุด |
| จุดที่ปัด | ปัดที่ระดับรายการ | ยอดจ่ายรายรายการคือตัวเลขที่พิมพ์ลงบิลและจ่ายจริง ถ้าปัดเฉพาะยอดรวม ผลรวมของบรรทัดจะไม่เท่ากับยอดท้ายบิล กลายเป็นข้อพิพาทกับ Agent |
| ฐานคอมมิชชัน | ยอดขายรวม (gross) | Agent ควรได้ค่าตอบแทนตามยอดที่ขายได้ ไม่ผูกกับโชคของรอบนั้น |

**ยังต้องให้ฝ่ายการเงินยืนยัน** — ถ้าคำตอบต่างจากนี้ ให้แก้ `MONEY_DECIMALS`,
`ROUNDING` หรือ `COMMISSION_BASE` ในไฟล์เดียว ไม่ต้องแก้ที่อื่น

### T-12 · เปลี่ยน isPermutation เป็น matchRule

boolean เดิมแทนรางวัลประเภท "วิ่ง" ไม่ได้ เพราะวิ่งตัดสินด้วยการที่เลขที่แทง
ปรากฏอยู่ในผลที่ออก ไม่ใช่การสลับตำแหน่ง จึงเปลี่ยนเป็น enum สามค่า
`EXACT` `PERMUTATION` `CONTAINS_DIGIT`

migration backfill ตามหลักการ ไม่ hardcode รหัสรางวัล — เดิมเป็นโต๊ดไป `PERMUTATION`
รับเลขหลักเดียวไป `CONTAINS_DIGIT` นอกนั้น `EXACT`

**ข้อจำกัดที่ต้องรู้:** ถ้าธุรกิจมีรางวัลที่ตัดสินด้วยกติกานอกเหนือจากสามแบบนี้
ต้องเพิ่ม MatchRule ใหม่ ไม่ใช่ดัดกฎเดิมให้พอใช้ — เป็นคำถามข้อ 1.3 ที่ยังไม่มีคำตอบ

### T-13 · จำกัด build worker เหลือ 4 ตัว

ค่าเริ่มต้นของ Next.js คือจำนวน CPU ซึ่งบนเครื่องพัฒนาเปิด worker พร้อมกัน 15 ตัว
แต่ละตัวโหลด Prisma client ของตัวเอง จน worker ตายด้วย
`FATAL ERROR: Zone Allocation failed - process out of memory`

CI บน Linux ไม่เจอปัญหานี้ แต่ตั้งไว้ให้เหมือนกันทุกที่จะคาดเดาง่ายกว่า

### T-10 · Cutoff job เป็น idempotent และป้องกันด้วย token

**เหตุผล** scheduler อาจเรียกซ้ำหรือเรียกถี่เกินไป งานต้องทนได้
และ endpoint ต้องไม่เปิดให้ใครก็เรียกได้ · ไม่ตั้ง `CUTOFF_JOB_TOKEN` เท่ากับปิดการใช้งาน
